# 交接：穩定性紀錄與自動驗證（給接手的 Claude）

使用者會貼「ABAI 穩定性紀錄」或自動驗證的結果給你。這份說明它們從哪來、怎麼看、目前還有哪些待確認的事。

## 使用者的固定規則
- 用繁體中文回答，白話。驗證過和沒驗證過的要分清楚。
- 每次改動前先自問四個問題：一定比較好嗎？有缺點嗎？真的認同要改嗎？能保證不弄壞嗎？不確定就先問。
- 每次回覆結尾附上兩個網址：
  `正式 app：https://jijiwo537-crypto.github.io/abai-newphoto/?v=<commit>`
  `最新測試網站：https://jijiwo537-crypto.github.io/abai-newphoto/order.html?v=<commit>`
- 有改 app 時，提醒使用者用「更新ABAI到手機」重新安裝。
- 不開 PR。commit 訊息不寫模型名稱。

## 部署
`npm ci` → `npx vite build` → `git apply --check .github/deploy-layout.patch` → commit → push 到開發分支和 main → `rm -rf node_modules dist`。

## 穩定性紀錄（設定 → 問題反饋 → 複製穩定性紀錄）
- 原生：`ios/App/App/StabilityPlugin.swift`
- 網頁：`utils/stability.ts`
- 紀錄只存在手機的 `Documents/stability.log`，不會外傳。
- 各種行的意思：
  - 「啟動 App」：每次開 App 記一筆。
  - 「⚠️ 網頁程序被 iOS 關掉後重新載入」：網頁那一層被系統收掉，等於使用者看到的閃退或白屏。後面附「被關掉前最後回報」，就是當時在哪個畫面、剩多少記憶體。
  - 「⚠️ 上次 App 沒有正常結束」：整個 App 閃退，或在背景被系統關掉。
  - 「記憶體警告」：系統發出的記憶體警告。
  - 「🧾 系統診斷／系統統計」：Apple MetricKit 的正式報告，系統最晚隔天才給。
  - 「網頁錯誤」：程式錯誤。
  - 「拍照：成品 W×H、RAW W×H，兩張畫面相差 N 毫秒…」：每次拍照的診斷。
  - 「匯入 RAW：…」：RAW 進編輯時有沒有拿到原生路徑、有沒有成功沖。
- 注意：
  - 網頁那邊用 `nativePlugin()`（`utils/nativeBridge.ts`）前，會先呼叫外掛的 `available()`。新寫的原生外掛一定要有 `available()`，不然網頁端會當它不存在。
  - 可用記憶體是整個 App 行程的數字，不是網頁那一層的上限。網頁那一層可能在數字還很高時就被關掉。

## 自動驗證
- 手機全面驗證：桌面的「ABAI全面驗證.command」，等同執行 `xcrun devicectl device process launch --device <手機> --terminate-existing com.abai.photo -abaiQA full-1`。
  - 腳本是 `utils/nativeQA.ts` 的 `scenarioFull`。
  - 一輪 10 項：修圖 4800 萬像素、批量、創意拼圖、編輯裡的拼圖（無縫＋整體特效）、美顏、仿色、藝術效果、跨頁拼圖、點陣文字、影片匯出。
  - 每項寫「全面驗證：開始：某某」和「✅／❌ 某某」，最後一行是「全面驗證結束：…」。
  - 網頁那一層中途被關掉的話，不會從頭重跑（`QAPlugin.swift` 的 `answered`），而是寫一行「⚠️ 自動測試中斷」。它上面最後一個「開始：」就是出事的那一項。
  - 測試照片由原生產生（`QAPlugin.makePhoto`），和從相簿選的照片一樣帶原生路徑。
  - 已知：修圖那一項腳本點不到「特效」，所以只測到濾鏡，紀錄裡會寫「找不到特效卡」。
- 手機壓力測試：「ABAI壓力測試.command」（`-abaiQA stress-N`）。
- 雲端：
  - `.github/workflows/regression.yml`：每次推 main 自動跑網頁回歸測試，腳本是 `tests/regression/core.mjs`。
  - `.github/workflows/ios.yml`：手動執行，`scenarios` 填 `full-1:1800`，就會在模擬器跑全面驗證。模擬器量不到記憶體，所以顯示 0MB。

## 2026-11-28 的改動與待確認
1. 大圖存檔（修圖／仿色／美顏）：導向上採樣分段計算（`utils/fullResExport.ts`）。成品逐位元相同。
2. 所有工具的 RAW 改用編輯器的 RAW 引擎、讀原生路徑（`utils/imageLoader.ts` 的 `developRawWithEngine`）。有 60 秒的放棄保護。
3. 拼圖、跨頁拼圖存 HEIC：改成把像素交給原生編碼（`utils/heicExport.ts`，`.abpx` 檔尾第 12 位元組＝1 代表 P3）。有顏色自我檢查和 60 秒保護。
4. 編輯裡用了人像或仿色後存檔：從最原始的原圖補廣色域和拍攝資訊（`ImageEditor.tsx` 的 `rootSrcOf`、`chainAligned`）。用了液化、修補、仿製、去痘這類會搬像素的操作，就不補色域（`BeautyStudio.tsx` 的 `beautyMovesPixels`，用白名單判斷）。
5. 成品頁按鈕閃白：`ExportActionLift.tsx`，等原生按鈕放上去之前先把網頁按鈕藏起來。
6. App 相簿匯出 RAW：直接寫 RAW 檔本身（`PhotoLibraryPlugin.swift` 的 `exportPhoto`）。
7. 相機 RAW：內嵌一張和照片一樣大的 JPEG 預覽（Apple WWDC21 的做法，`NativeCameraPlugin.swift`）。目的是讓「照片」App 裡的 RAW 不再模糊。
   - **待確認：** 在真機拍照會不會閃退、照片 App 裡是否變清楚。萬一閃退，就拿掉 `rawEmbeddedThumbnailPhotoFormat` 那一段。
8. 已知風險，還沒處理，等使用者決定：從「檔案」App 或分享進來、沒有原生路徑的 4800 萬像素照片，在修圖裡可能讓網頁那一層被系統關掉。
9. 使用者決定不做：抖動（dithering）、全面原生重寫。

## 2026-11-29 真機全面驗證結果（重要，接手先看這段）
- 修好「不重跑」之後的第一輪：在「編輯裡的拼圖：5 張、無縫＋整體特效」按下儲存的瞬間，網頁那一層被 iOS 關掉了。
  - 舊的那輪測試照片是網頁做的，同一項有過；這次換成原生產生、帶原生路徑的照片，就在存檔時被關掉。
  - 這是真的 app 問題：拼圖套整體特效後存檔，記憶體高峰在網頁層。
  - 之前在桌機上量過：存檔前已經佔約 216MB，整體特效那一步又同時開了 3 張和成品一樣大的暫存畫布（`applyGlobalInPlace` → `applyPhotoFx` 的 out／`effectInputs` 的 source／`applyGlEffects` 的 surface）。成品 4096 以上時，光這 3 張就超過 270MB。
  - 修法方向：讓整體特效分塊處理（要處理光暈這類跨塊效果的邊緣），或在存檔前先放掉預覽用的快取。成品要和預覽一樣，用 `tests/regression/core.mjs` 的 collageSeamless 驗證。
- 修圖和批量的成品顯示成 2560 長邊：那是成品頁顯示用的預覽（原生存檔會另外出一張 PREVIEW_PX 的小圖），不是實際存檔的尺寸。測試目前讀不到真正存出來的檔案大小。
- 「⚠️ 上次 App 沒有正常結束」緊接在啟動指令後面出現時，是指令的 --terminate-existing 把 App 關掉造成的，不是真的閃退。
